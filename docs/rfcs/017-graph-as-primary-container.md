# RFC-017: Graph as the Primary Container

**Status**: Implemented (S1.5 + S2 shipped; S3 partial — schema wired, canvas stubbed)
**Author**: Invana Team
**Date**: 2026-05-21
**Supersedes (partially)**: RFC-012 (Mission-Centric Architecture)

---

## Problem

The current MVP (per `docs/internal/mvp.md`) defines a three-layer hierarchy:

```
User → Workspace → Mission → GraphConnection (the DB binding)
```

This was inherited from RFC-012, which inverted the original graph-connection-centric model to a mission-centric one and then added Workspaces as a sharing/membership boundary above Mission.

Two problems with this shape, both surfaced now that we are pre-release on `arch/redesign`:

1. **"Workspace" is generic.** Invana is a graph platform. The user-facing unit of work is *the knowledge graph itself* — not an abstract workspace that happens to contain one. Naming the top-level entity after the thing it produces is clearer, and the brand benefits.
2. **"Mission" is a sub-layer the user does not need.** In practice, every Mission in MVP is 1:1 with a graph connection, a stitched knowledge graph, and a set of analysis bindings (skills, agents, LLMs, datasets, objectives). The Workspace/Mission split adds a routing layer and a foreign-key column without giving the user a meaningful choice. Collapsing them removes a layer from URLs, the data model, and the mental model.

There is also a naming collision: the existing `Graph` entity (in `engine/src/invana/graphs/models.py`) describes a *graph DB connection*, not a knowledge graph. The word "graph" in the codebase is overloaded across (a) DB connection, (b) schema/model, (c) the stitched knowledge graph payload, and (d) rendered output. This RFC fixes that overload at the source.

---

## Decision

Collapse the three-layer hierarchy into a two-layer one:

```
User → Graph (1:1 GraphConnection)
```

**`Graph` is the primary container.** It carries everything that previously lived on Workspace *and* everything that previously lived on Mission: membership, invitations, the DB connection (1:1), schema, datasets, objectives, instructions, skills, agents, LLM bindings, criteria/outcomes.

**`Mission` is removed as an entity.** Its fields and bindings move onto `Graph`.

**The existing `Graph` model is renamed to `GraphConnection`** and becomes a 1:1 child of `Graph` carrying connection settings only (URL, auth, driver, encrypted secrets). A `Graph` row without a paired `GraphConnection` is not valid in MVP.

**Nothing sits above `Graph` in MVP.** Users have memberships directly on Graphs. Org/team grouping is a post-MVP problem solved by adding a nullable `owner_org_id` later — not pre-planned now.

**Users get a `username`.** Globally unique, required at registration. Graph URLs are `/u/:username/:graphSlug` (e.g. `/u/ravi/customer-analysis`). The `/u/` prefix namespaces all user-content URLs under a single segment, so usernames cannot collide with Studio's top-level routes (`/admin`, `/settings`, `/login`, etc.) — no reserved-name list is needed beyond `u` itself. `graphs.slug` is unique per user, not globally — two users can both have a graph slugged `analysis`. The URL path parameter is named `graphSlug` everywhere in routing code (router paths, `useParams`, helper signatures, hook arg keys); the underlying data field is still `Graph.slug`. The verbose param name disambiguates from generic "slug" elsewhere in the codebase.

**Username is mutable.** A user can change their `username`; existing URLs under the old username 404 (no redirect table). Trade-off accepted in exchange for implementation simplicity. Implementation should rate-limit changes (e.g. once per 30 days) to discourage abuse and reduce churn on shared links.

**Graph creation is a two-stage flow.** The create modal collects only `name`, `slug` (autogenerated from name, editable), and `intent`/`instructions` — that's enough to create the row. On landing in the graph detail page, the user is taken through a setup wizard with sections: **Graph Info** (incl. connection), **Intent**, **Skills**, **Datasets**. Until every required section is completed, the modeller, explorer, and query console are gated behind the wizard.

## Rename map

| Old | New | Notes |
|---|---|---|
| `Workspace` (entity, table `workspaces`) | `Graph` (table `graphs`) | absorbs Mission's fields |
| `WorkspaceMember` (table `workspace_members`) | `GraphMember` (table `graph_members`) | role enum unchanged |
| `workspace_role` enum | `graph_role` enum | values: `developer` \| `analyst` \| `admin` |
| `Invitation.workspace_id` | `Invitation.graph_id` | scope unchanged (per-graph invites) |
| `Mission` (entity, table `missions`) | **removed** | fields move to `Graph` |
| `Graph` (entity, table `graphs`) — connection | `GraphConnection` (table `graph_connections`) | 1:1 child of `Graph` |
| `GraphConnectionForm` (Studio) | unchanged | name already correct |
| `GraphSchema` (entity) | unchanged | now naturally means "schema of the Graph" |
| `/workspaces/:slug/...` | `/u/:username/:graphSlug/...` | per-user namespaced |
| `/missions/{mid}/...` | folds into `/u/:username/:graphSlug/...` | no separate mission segment |
| `personal workspace` (auto-created by `invana init`) | **removed** | `invana init` creates the root user only; user creates their first Graph manually |

## Data Model

### `users` — added column

```
username    String(64)   UNIQUE NOT NULL   (case-insensitive, [a-z0-9-], 2–64 chars)
```

Validation: lowercase, alphanumerics + hyphen, no leading/trailing/consecutive hyphens. Mutable, but rate-limited (e.g. one change per 30 days; final number at implementation time). No reserved-name list needed — the `/u/` URL prefix isolates usernames from Studio's top-level route namespace.

### `graphs`

Absorbs the former `workspaces` table plus the analytical fields from `missions`.

```
graphs
──────────────────────────────────────────────────────
id                UUID PK
slug              String(255)   NOT NULL
name              String(255)   NOT NULL
description       Text          nullable
intent            Text          nullable    (markdown — captured at creation)
objectives        Text          nullable    (markdown)
success_criteria  Text          nullable    (markdown)
setup_state       JSONB         NOT NULL    (per-section completion flags; see Setup Wizard)
status            Enum          active | archived     default active
created_by_id     UUID FK → users.id     ON DELETE RESTRICT
created_at        DateTime
updated_at        DateTime
UNIQUE (created_by_id, slug)
```

### `graph_connections`

1:1 with `graphs`. Carries the DB binding only.

```
graph_connections
──────────────────────────────────────────────────────
id                UUID PK
graph_id          UUID FK → graphs.id  UNIQUE NOT NULL  ON DELETE CASCADE
driver            String        NOT NULL    (cypher / gremlin variant)
url               String        NOT NULL
auth_encrypted    Bytes         nullable    (Fernet, INVANA_ENCRYPTION_KEY)
options           JSONB         nullable
created_at        DateTime
updated_at        DateTime
```

### `graph_members`

```
graph_members
──────────────────────────────────────────────────────
id            UUID PK
graph_id      UUID FK → graphs.id    ON DELETE CASCADE
user_id       UUID FK → users.id     ON DELETE CASCADE
role          graph_role             NOT NULL
created_at    DateTime
UNIQUE (graph_id, user_id)
```

### `invitations`

```
invitations
──────────────────────────────────────────────────────
id            UUID PK
graph_id      UUID FK → graphs.id    ON DELETE CASCADE
email         String(320)            NOT NULL
role          graph_role             NOT NULL
token_hash    String(64)             NOT NULL  (sha256)
created_by_id UUID FK → users.id     ON DELETE RESTRICT
expires_at    DateTime
created_at    DateTime
```

All other entities previously scoped to `mission_id` (datasets, skills, instructions, llm_providers, agents, criteria, outcomes, import_jobs, stitch_jobs) are re-scoped to `graph_id`. None of these are built yet on `arch/redesign` per memory — only Layer 1 has shipped — so this is a forward change, not a migration of existing data.

## URL Surface

All graph-scoped routes are namespaced by `:username/:graphSlug`.

| Concern | URL |
|---|---|
| Username availability | `GET /api/v1/auth/username-available?username=foo` (unauthenticated; returns `{available: bool, reason?: string}`; rate-limited by IP) |
| Create / list graphs | `POST /api/v1/graphs` · `GET /api/v1/graphs` (lists graphs the caller is a member of) |
| Graph detail | `GET /api/v1/u/{username}/{graphSlug}` |
| Graph members | `GET /api/v1/u/{username}/{graphSlug}/members` · `PATCH .../members/{user_id}` · `DELETE .../members/{user_id}` |
| Invitations | `POST /api/v1/u/{username}/{graphSlug}/invitations` · `GET .../invitations` · `DELETE .../invitations/{id}` |
| Connection | `GET /api/v1/u/{username}/{graphSlug}/connection` · `PUT .../connection` |
| Schema (modeller) | `GET /api/v1/u/{username}/{graphSlug}/schema` · `PUT .../schema` |
| Query console | `POST /api/v1/u/{username}/{graphSlug}/query` |
| Datasets | `/api/v1/u/{username}/{graphSlug}/datasets/...` |
| Skills / Instructions / LLM / Agents | `/api/v1/u/{username}/{graphSlug}/{skills,instructions,llm,agents}/...` |

Studio routes mirror this: `/u/:username/:graphSlug/{settings,modeller,explorer,query,datasets,agents,...}`.

## Graph Setup Wizard & Feature Gating

A Graph progresses through setup before its analytical features are usable.

**Create modal** (one-shot, creates the row):
- `name` (required)
- `slug` (autogenerated from name, editable; validated unique per owner)
- `intent` (required, markdown — short statement of what the Graph is for)

After submit, the user lands on `/u/:username/:graphSlug` and enters the setup wizard.

**Setup sections** (each writes to `graphs.setup_state.{section}.completed_at`):

| Section | Completion criterion | Required? |
|---|---|---|
| Graph Info | `name`, `slug`, `intent` present + `GraphConnection` configured and reachable | Yes |
| Intent | `objectives` and/or `success_criteria` filled | Yes |
| Skills | ≥1 Skill defined **or** explicitly marked "none for now" | Skippable |
| Datasets | ≥1 Dataset attached **or** explicitly marked "none for now" | Skippable |

A "skipped" section writes `setup_state.{section}.skipped_at` instead of `completed_at`; both states count as cleared for wizard progression.

**Gating:**
- **Modeller, Explorer, Query console** — unlocked as soon as `Graph Info` is complete (working connection). A user can model and query a fresh, empty graph without first attaching datasets or defining skills. This matches the natural workflow: design the ontology, then load data conforming to it.
- **Agents (runtime)** — additionally require Skills and Datasets to be cleared (completed or explicitly skipped). Skipping both still permits agent creation, but agent *runs* will fail-fast with a clear error if there are zero skills or zero datasets bound; nothing structural blocks the user from getting there.

The wizard is **resumable** — the user can leave and return; the detail page shows progress and which section to complete next.

## MVP Impact (`docs/internal/mvp.md`)

Every layer except Layer 1 is currently unbuilt, so the impact is mostly a doc edit:

- **Layer 1 — Identity & Access (shipped)**: rename in place. `Workspace` → `Graph` across entities, routes, Studio pages, admin views. Add `users.username` (required at registration and `invana init`). **Remove the auto-created personal workspace** from `invana init` — it creates the root superuser only; the user creates their first Graph manually. Behavioral semantics (role scoping, sole-admin guards, invitation flow) are unchanged.
- **Layer 2 — "Workspace registries"**: renamed to **Graph settings**. Connectors registry and LLM providers are Graph-scoped settings, not a separate registry concept.
- **Layer 3 — Missions + bindings**: **deleted as a layer.** Objectives, instructions, skills, LLM bindings, agents move onto Graph directly. The "mission settings" tabs become Graph settings tabs.
- **Layers 4–9** (Datasets, Modeller/Stitcher, Knowledge Graph, Explorer, Agents, Criteria/Outcomes): every `mission_id` FK becomes `graph_id`. URL prefixes drop the `/missions/{mid}` segment.
- **Slice S3 (Graph DB binding)**: collapses into Graph creation. There is no separate "bind a connection to a mission" step — creating a Graph either provisions its `GraphConnection` inline or the Graph is in an "unconfigured" state until one is supplied.
- **Slice renumbering**: the S0 → S12 plan re-numbers once mission-related slices fold in. Concrete renumbering happens in the `mvp.md` edit, not here.

## Migration

Pre-release on `arch/redesign`, per existing branch policy (RFC-012, MVP doc): **Alembic history is reset.** No data migration, no backwards-compatibility shims, no `// removed` markers in code. The rename is mechanical across the engine, Studio, admin views, CLI, and docs in a single coordinated change set.

## Alternatives Considered

| Alternative | Why rejected |
|---|---|
| Keep `Workspace`, rename only the inner `Graph` → `GraphConnection` | Doesn't fix the "what *is* the unit of work" question. Workspace stays a generic container in a graph-native product. |
| Use `GraphSpace` instead of `Graph` | Avoids the rename of the existing `Graph` model, but stacks "Graph*" naming awkwardly (`graph_space_members`, `/graph-spaces/:slug/...`) and keeps the original overload of `Graph` (= DB connection). Renaming to `GraphConnection` is a one-time cost that pays back permanently. |
| Use `Atlas` (collection-of-graphs metaphor) | Loses the brand echo and the literal mapping to "the knowledge graph the user is building." Introduces a new term users have to learn. |
| Keep Mission as a sub-layer of Graph | Adds a layer that, in MVP, every Graph would have exactly one of. No user-visible choice → dead complexity. |
| Pre-plan an Org / Team layer above Graph | Speculative scaffolding (CLAUDE.md: don't design for hypothetical future requirements). Add nullable `owner_org_id` later when actually needed. |
