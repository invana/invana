## Findings

| Severity | Where | What | How to fix |
|---|---|---|---|
| should-fix | `plugins/queue.py` `await_outcome` + `runtime/executor.py` `RebuiltContexts.open` | After `transient · worker_unavailable` the envelope stays queued. A worker that starts later still runs it, because `RebuiltContexts` never checks that the step is still `running` at the envelope's `attempt`. For `mail.send` this means mail goes out after the run was told the step failed. If the step is then retried, `attempt + 1` gives a new idempotency key, so a second mail goes out with a different `Message-ID`. The "redelivered send is the same message" seam only covers the same attempt | Before running, check in `run_tool_envelope`/`RebuiltContexts` that the step row is `running` and `row.attempt == envelope.attempt`. If not, record nothing and return. Alternatively, cancel the procrastinate job on timeout. Add the case to the Seams table |
| should-fix | `docs/…/tool-plugins.md` TP4 vs `docker/` · `Dockerfile` | TP4 says "Production images set `procrastinate`", but no compose, Dockerfile or worker service was changed. The entry admits this. As shipped, every image runs tool steps inside the API process, which contradicts the user story ("that code never runs inside the API process") | Either set `INVANA_EXECUTOR=procrastinate` and add a `worker` service to the production compose/image in this slice, or reword TP4 and the story to say images default to `inline` until a named later slice |
| should-fix | `runtime/managers/skill_seed.py` `ensure_plugin_skills` | Skills are seeded from every *loaded* plugin, whether it is enabled or not. *Collect a dataset from the web* is therefore written into every Graph while `invana.tools.web` is disabled, which is the default. Its plan will name `web.*` steps that fail `plugin_disabled` | Seed a tool plugin's skills only when it is enabled (and on enable). If seeding stays unconditional, record that in TP13 and make sure the skill reads as unavailable while its plugin is off |
| should-fix | `tests/runtime/test_tool_dispatch.py` | The send gate has a positive test (hold → approve → send) but no decline test. C10's negative path, "declined → `blocked · send_declined`, nothing sent", is unproven. The entry lists this as a gap | Add one test: hold → decline → the step fails `send_declined` and the task body never ran |
| note | `runtime/interpreter/loop.py` `_hold_for_send` | The approver is `v.actor_id or v.graph.created_by_id`, and `""` when there is neither. | note | `runtime/executor.py` `envelope_for` | Carried over from the B14 review: the envelope's `task` is the *current* `key@version`, not the plan's pinned `Task.task_version`.
