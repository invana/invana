## Findings

| Severity | Where | What | How to fix |
|---|---|---|---|
| should-fix | `activity/querysets/notifications.py` `CursorQuerySet.events_after` · `managers/notifications.py` `EventMatcher.match_new` | The cursor advances on `(created_at, id)`, and `created_at` is stamped in Python when the row is inserted, not when it commits. Take an event inserted at t1 by a transaction that commits at t3. A tick at t2 reads newer committed events and moves the cursor past t1, so that event is never matched. A `run.finish · failed` from a slow transaction can drop silently, which breaks NT2 ("matching runs after commit … through a persisted cursor"). | Read only events older than `now − lag` (a few seconds, longer than the longest write transaction), or key the cursor on a commit-ordered sequence. Record the choice as a Decision in notifications.md. |
| should-fix | `activity/managers/schedules.py` `fire_due` → `_open` | `run_all` combined with the default overlap `skip` replays only one missed firing. The first `_open` flushes a run that is not yet terminal, so `last_opened` sees it and every later missed firing in the same tick is skipped with *the previous run is still going*. C5 promises "every missed one, at most 24". | Leave the overlap check out of the firings that one `fire_due` call opens for the same schedule. The other option is to make the interaction explicit in schedules.md (SC4/SC5). Add one test that combines `run_all` and `skip`. |
| should-fix | `activity/managers/notifications.py` `EventMatcher._notify` | Private-project filtering (NT8) is applied only to inbox recipients. Channel deliveries for an event on a private project still go to Slack, webhook or email: the rule name, the action and status, the actor's name and the run link. Everyone in that channel learns that the run exists and how it ended. | Do not send channel deliveries for `event.project_id` in a private project. Or, if sending is intended, write it as a Decision and a Seam in notifications.md ("a channel is not a person; private-project events never leave the inbox"). |
| should-fix | `activity/managers/approvals.py` `decide` | The *decided twice* seam says the 409 "names who decided first". The message is `Already approved.` and names nobody. | Add the decider's username, e.g. `Already approved by ada.` The `Members.usernames` lookup is already there. |
| note | `activity/managers/approvals.py` `list` · `server/approvals/views.py` | `?mine=true` returns every status, with pending first. C6 says "pending, nearest deadline first". The CLI's `list` help says *Pending*. Filtering `mine` happens in Python after a `limit=500`. | Default `mine=true` to `status=pending`, or reword C6. Filter `approver_ids` in SQL (`ANY`) before the limit. |
| note | `activity/managers/schedules.py` `fire_due` (queued) | A firing queued with *run now* opens even if the schedule was paused after it was queued. This is harmless, but C9 does not say it. | One line in C9: *run now* on a paused schedule is allowed, or refused (409). |
| note | notifications.md › Engine | The `notifications` table and `NotificationRead` carry `schedule_id`, but the Engine row does not list it. | Add `schedule_id` to the row. |
| note | Gates not run (stated in the session log) | Graph-DB suites, the full engine suite, migration 071 up and down on the dev Postgres, and a firing end to end through a live LLM. | Run them before C05 builds on this. |
